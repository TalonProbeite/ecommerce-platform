# Схема каталога аренды

Проект локальный, сохранение прежних данных не требуется. Схема создаётся
семью миграциями: `stores`, `categories`, `products`, `stocks`,
`product_attributes`, `product_images`, `stock_reservations`. Все ограничения
определены непосредственно в миграциях создания этих таблиц; отдельной миграции
обновления схемы нет. На пустой PostgreSQL выполняется `php artisan migrate`.
Денежные поля `price_per_hour` и `deposit_amount` хранят целое число копеек.

## Целостность

- `(store_id, slug)` уникален у товаров, включая soft-deleted записи.
- UNIQUE `(id, store_id)` на категориях и товарах поддерживают составные FK.
  Родитель категории, категория товара, склад и резерв должны относиться
  к той же компании, что и связанная сущность.
- Удаление компании с категориями/складами, товара со складом/резервами и
  используемой категории блокируется FK. Удаление родительской категории
  обнуляет только `parent_id` дочерних категорий, сохраняя их `store_id`.
  Синтаксис `ON DELETE SET NULL (parent_id)` проверен на PostgreSQL 16,
  используемой в Docker Compose проекта.
- Исходные CHECK количественного склада сохраняются. Один склад на товар
  обеспечивается существующим UNIQUE `stocks.product_id`.
- Partial unique index разрешает не больше одного главного изображения товара.
  `product_images.object_key` остаётся ключом объекта S3-совместимого хранилища.
  Изображения упорядочиваются по `created_at`, затем по `id`; отдельной колонки
  `sort_order` нет.
- `order_id` принадлежит внешнему Order Service, FK на заказы отсутствует.
  UNIQUE `(order_id, product_id)` также обеспечивает индекс для поиска по
  `order_id`; отдельные индексы покрывают `product_id` и `(store_id, status)`.

Полей `rating` и `reviews_count` в текущей схеме нет: каталог не хранит
агрегированный рейтинг, а витрина подставляет нейтральные значения. Даты аренды
имеют тип TIMESTAMPTZ и immutable casts; модель сохраняет смещение часового пояса
при записи.

`Stock::stockReservations()` использует уникальный `product_id` склада как
локальный ключ. Составные FK обоих типов записей на товар гарантируют одинаковый
`store_id`, поэтому связь корректна и при eager loading. Обратной составной связи
`StockReservation::stock()` нет. Существующие имена `Product::attributes()` и
`Product::images()` сохранены; характеристики следует получать через relationship
метод или eager loading, учитывая внутреннее поле `$attributes` Eloquent.

## Создание схемы и откат

Категории создаются до товаров, товары — до складов, характеристик, изображений
и резервов. UNIQUE `(id, store_id)` создаётся до FK, который на него ссылается.
Самоссылочный FK категорий добавляется после создания таблицы и её UNIQUE.
`parent_id` nullable, поэтому корневым категориям не нужен искусственный родитель.

Откат удаляет таблицы в обратном порядке зависимостей; повторное применение
создаёт чистую схему. Уже выполненные исходные миграции не обновляют локальную
БД повторным `migrate`: для новой структуры следует использовать пустую БД
или пересоздать локальную схему, если прежние данные не нужны.

## Проверка тестов

Юнит-тесты не требуют PostgreSQL и запускаются на хосте:

```sh
make test-unit
```

Feature/integration-тесты выполняются в Docker на локальном Compose-стеке.
`make test` сам поднимает `catalog-db`, создаёт отдельную БД `catalog_test`,
пересобирает образ приложения из текущих исходников и запускает весь набор:

```sh
make test          # Unit + Feature
make test-feature  # только Feature/integration
```

Имя тестовой БД можно переопределить: `TEST_DATABASE=my_test_db make test`.
Оно должно содержать `test` или `testing`, иначе тесты будут пропущены.
Каждая проверка создаёт собственную пустую схему `catalog_test_<uuid>`,
запускает все семь миграций и добавляет тестовые записи. После проверки
удаляется только эта временная схема. Проверки охватывают ограничения, типы,
индексы, relationships, полный откат и повторное создание схемы.

## Форматирование

Laravel Pint использует исходный `pint.json` с preset `psr12`. Правило
`array_syntax` настроено объектом `{"syntax": "short"}`: строка `"short"`
не является допустимой конфигурацией правила и вызывала ошибку до форматирования.
